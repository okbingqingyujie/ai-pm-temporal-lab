# AI 说已完成，为什么文件还打不开？

AI 产品经理精选 · 2026-11-23 · 开源项目与交付验收

**列表上的“完成”、工作流的“完成”，都不是用户拿到文件的证据。** 做一个导出产品，要先回答：这份文件是不是当前那一版、是否确实可读，以及现在这个用户能不能下载？

这是一份独立原创中文学习笔记，不是 Temporal 官方教程、源码镜像或线上复盘。以下三页简报及所有事件均为虚构纸面练习；没有安装、运行或部署 Temporal，没有生成实际文件或执行验收。

## 1. Temporal 是什么，为什么现在读？

[Temporal](https://github.com/temporalio/temporal) 用来编排长任务。开发者可以定义由多个步骤组成的工作流，利用执行历史和恢复机制处理进程中断等情况。它记录工作流发生了什么，却不了解你的产品把什么定义为“已交付”。

- **上游快照：**2026-11-23 北京时间核查，[GitHub API](https://api.github.com/repos/temporalio/temporal) 返回 **24,566 Stars**；项目公开、未归档，当日仍有仓库推送。关注度不代表你的交付体验可靠。
- **版本与许可：**[v1.32.2](https://github.com/temporalio/temporal/releases/tag/v1.32.2) 是本次核查的最新正式服务端版本，2026-11-02 18:38 UTC 发布。已读该标签的 [README](https://github.com/temporalio/temporal/blob/v1.32.2/README.md) 和 [MIT LICENSE](https://github.com/temporalio/temporal/blob/v1.32.2/LICENSE)。该版本证明项目近期维护，不是下述索引行为的首次上线；不把服务端版本、SDK 和托管套餐混为一谈。

[官方 Visibility 文档](https://docs.temporal.io/visibility#how-current-is-visibility-data)说明：工作流列表和计数使用异步更新的搜索索引，因此可能看到旧状态，不能按“最多等几秒”设计承诺。需要某次执行的当前状态时，官方建议用 `DescribeWorkflowExecution`，不依赖这个索引；要响应工作流进展，可以参考[执行历史](https://docs.temporal.io/encyclopedia/event-history)。**获取了执行状态，仍没有证明工作流外部的文件能打开。**

## 2. 一次导出，要看三份证据

设想用户让 AI 生成一份三页 PDF 研究简报。为了练习，工作流负责生成内容；存储校验和下载由应用的交付层管理。这个分工是虚构场景，现实产品也可以让工作流等待交付校验完成再结束。本例不是在描述 Temporal 的缺陷。

| 哪个信号 | 可以证明什么 | 不该顺手推出什么 |
| --- | --- | --- |
| 列表：上一份可用状态副本 | 最近一次同步时，任务显示到哪一步 | 当前已成功、已失败，或列表中找不到就不存在 |
| 详情：按任务绑定查询本次工作流 | 对应 Workflow ID／Run ID 的执行进度或终态 | 文件存在、是当前版本，或当前用户有权打开 |
| 产物记录：应用核验了具体文件 | 当前版本已写入指定对象，并通过所需完整性和打开检查 | 此后永远可下载、内容事实审核通过或用户已经拿到 |

**推荐交付证据：**应用保留任务 ID、当前产物版本、已验证文件的对象版本或不可变标识、检查时间和结果。模拟验收可以要求文件能完整读回、能解析为恰好三页 PDF、内容标识对应当前任务。只看文件名、路径、存在标记或工作流的成功回执不够。文件能打开不等于内容正确，如需事实审核另设标准。

下载服务实际发出文件时再核查访问权限与请求版本，并通过已验证的对象标识读回内容，不悄悄把“当前”替换成老版本。旧版若允许下载，也必须是明确标出的历史入口，而不是当前按钮的兜底。撤权可阻止后续受控访问，不能保证收回之前已下载的副本。

## 3. 列表、聊天和详情怎么说才一致？

它们不必同时刷新，但都要忠实表达证据。

- **列表显示快照。**标记“上次同步”或“查看当前状态”。如果副本还在生成中，用户仍可以打开详情；不要靠改颜色掩盖两处的时间差。
- **聊天与详情不各猜一个结果。**打开详情时按任务绑定读取当前执行与当前文件。已确认当前尝试成功生成内容、但产物还未验证，才显示“内容已生成，正在准备下载”。失败、取消、未知或仅见流程终态都不能支持这个说法。应用确认当前版本已准备好且该用户有权限后，才显示“可下载”。
- **区分明确失败和暂时未知。**文件检查确认失败就说明导出失败，并给下一步；状态读取超时且没有独立证据确认当前文件，显示“暂时无法确认下载状态，点击重试”。不要把旧“可下载”的卡片样式当成有效证据。
- **用服务端版本顺序，不用到达顺序。**应用应把已接受状态变更合成为同一任务的单调递增修订号；客户端丢弃更旧的任务快照。服务端还需在记录就绪前比较当前产物版本与该结果的任务／尝试绑定。不能为刚到达的旧版本结果直接分配更大的修订号，让它伪装成新状态。这里的修订规则是应用设计，不是 Temporal 自带的全局顺序保证。

## 4. 纸面走查：两种状态策略，用同一条事件时间线

- **A：快照组。**列表和聊天按各自手里的执行标记显示“完成”；详情和按钮沿用已读快照。
- **B：证据组。**复用同样界面、输入、文件与故障，只调整界面状态依据：区分列表副本和详情核验，按当前绑定决定是否显示可下载。
- **两组共用同一个安全下载关卡。**下载服务始终按当前版本与授权检查。用桩另记客户端请求了哪一版，与服务最终交付哪一版分开；A 可能误显示或尝试错版，但不能真的发送错版。点击前后状态改变属于共享关卡的独立回归，不归功于 B 的界面。

固定任务 `S17`，首次 PDF 为 `v1`，重新生成后为 `v2`。为每一案写出真实状态顺序、两个界面看到的时间及预期下载对象。不要只用“过了十秒”判断哪一方正确。

| 用例 | 合成事件 | 要验收的证据 |
| --- | --- | --- |
| T1 列表滞后 | 列表仍“生成中”，详情的当前文件已通过验证 | 旧列表不妨碍进入详情；当前版本可下载。分别记录实际就绪与列表更新 |
| T2 执行早于文件 | 工作流已完成，但当前文件还在写入或未核验 | 详情是“正在准备下载”，不提前显示可下载；核验后正常放行 |
| T3 迟到的旧完成 | v2 已接替 v1，v1 就绪通知后来才到 | 应用不把 v1 设成当前，旧快照不覆盖新状态；待 v2 核验后只能交付 v2 |
| T4 当前状态查不到 | 缓存卡片显示可下载；当前读取失败，缺少独立证据确认当下版本、产物就绪或授权 | 保留上次时间但明确“暂时无法确认”；不直接按旧卡片交付 |
| T5 正常交付 | 当前版本 v2 可读、完整且用户有权访问 | 能拿到确切的 v2，测试端能解析三页，不能靠全部隐藏按钮达标 |
| T6 文件坏了 | 对象路径存在，但只写入部分或读取到错误标识 | 本轮不能标可下载；如果先前通过、现在读取失败，报告故障，不偷换老版本 |
| T7 显示后撤权 | 页面曾显示可下载，点击前访问权已变更 | 服务端阻止新读取，界面更新或提示无访问权；不把拒绝说成文件不存在 |

上表的输出都是拟定验收，不是跑过结果。T6、T7 说明“曾经就绪”与“本次下载成功”是不同观测，不保证任意点击都在同一时刻完成。

## 5. 指标与产品决策

- **错误就绪。**统计展示为“可下载”时，依据屏幕渲染所对应的状态时点，实际还未通过验收或属于错版的次数；期间另发生撤权或删除的情况，按点击竞态另报，不倒算成先前时点撒谎。
- **正确交付。**记录请求到了哪一版、授权结果、服务输出标识及测试端能否读开。至少报告正确版本交付率及错版或越权交付数。误显示、尝试错版但被安全关卡拦住、实际发错文件分开计；零错版不能替代正常路径可用。
- **把三段时间拆开。**执行完成 → 产物首次验证就绪；产物就绪 → 用户看到可用；用户点击 → 成功打开。分别报告延迟、失败与未知；不要把索引晚同步算成文件生成慢。
- **示例门槛。**B 组零提前承诺，验证中、失败和未知有不同文案；两组共享下载关卡都要零错版或越权交付。B 的正常案与列表滞后案都能打开当前文件；不能以压掉所有按钮换来零错误。有限脚本不代表线上失效率或 SLA。

没有真实下载凭据、对象版本或读回证据的场景，评审结论就是“交付待确认”。如果只需查看一个任务，不必为了仪表盘的快照复杂化下载路径；把准确性留给真正影响决策和交付的那一步。

### 面试怎么说

“我会把长任务的列表快照、执行状态和产物可用性分开。流程结束只说明它记录的工作做完了；文件要按当前版本读回核验，点击还要重新检查权限。验收既看零过早承诺、零错版，也要验证正常用户确实取得当前文件。”
